# Risk Review

This document explains the design of the risk review workflow: how decision packages are built, why the AI recommends but never decides, how separation of duties is enforced, and the trade-offs involved.

## Decision Package Design

A decision package is the structured output produced when an operator asks the system to analyze a risk item. It bundles everything a reviewer needs to assess the risk in one place, before any human casts a vote.

The package is generated by a LangGraph `StateGraph` in `backend/app/services/decision_package.py`. The graph has three stages:

1. **Completeness check.** Before calling the LLM, the pipeline inspects the risk item for required fields: a meaningful description (at least 30 characters), a proposed mitigation, and a named owner. If any are absent the pipeline short-circuits and returns the package with `needs_info=true` and a list of specific gaps. No LLM call is made and no assessment can be submitted until the gaps are resolved. This prevents the AI from producing plausible-looking analysis on incomplete inputs.

2. **Perspective generation.** The pipeline calls the provider-agnostic LLM layer to produce three structured perspective analyses: security, compliance, and business. Each perspective includes key concerns, reviewer questions, a confidence score, and a rationale. The LLM layer supports OpenAI structured output and Anthropic tool use. When no API key is configured it falls back to deterministic placeholder perspectives so the demo runs at zero cost. The `source` field in the package records which path was taken (`openai_structured_output`, `anthropic_messages`, `fallback_no_provider`, `fallback_invalid_output`, `fallback_provider_failure`, `fallback_unexpected_failure`, or `seed`).

3. **Similar-case retrieval.** The pipeline encodes the risk description as a vector and queries pgvector for the most similar past decided risks. Results are ranked by cosine similarity score descending and attached to the package as `past_decisions`. Reviewers can use these as precedent when forming their own view. In the demo environment the embeddings are computed with a deterministic local function so no external service is called.

The package also records `risk_score` (impact × likelihood, 1-25), `recommended_treatment` (accept / mitigate / transfer / avoid), and whether any safety flags were raised during generation.

## Why the AI Recommends but Never Decides

The package sets `needs_human_decision=true` unconditionally. No code path allows the LLM to write to the `decisions` table or change a risk item's status to `decided`. This is a hard invariant enforced at the application layer, not a model-level instruction.

There are three reasons for this:

**Accountability.** A decision to accept or treat an organizational risk has real consequences. The decision needs a named human owner who can be held accountable if the risk materializes. An LLM output cannot serve that function.

**Auditability.** Every decision is written to the audit log with the deciding user, their role, a rationale, the package id, and a version stamp. A future auditor can trace exactly who decided what and on what basis. LLM outputs are not auditable in the same way: the same model with the same input can produce different outputs, and the model itself changes over time.

**Quality of the assessment.** The AI produces perspectives by reasoning about the text it receives. Reviewers bring contextual knowledge the AI cannot have: organizational priorities, in-flight controls, budget constraints, regulatory history, and personal accountability. The package is a structured prompt to that human judgment, not a replacement for it.

## Separation of Duties

The decision endpoint enforces two separation-of-duties rules:

1. **Two qualifying assessments are required.** A decision cannot be recorded unless at least two distinct reviewers have submitted assessments against the package.

2. **The deciding manager's own assessment does not count.** If the user making the decision also submitted an assessment, that assessment is excluded from the qualifying count. This prevents a single person from both reviewing and deciding, even if they have the manager role.

These rules are checked in `backend/app/routers/risks.py` before any write is committed. The endpoint returns HTTP 422 with a structured error body that names the deciding user and the current qualifying count, so the frontend can surface an actionable message.

The RBAC roles that can make a decision are `manager` and `admin`. Operators and viewers can submit assessments but not decisions. This means the minimum workflow requires at least three distinct users: one operator to create the risk and generate the package, two reviewers to assess it, and one manager to decide.

## Trade-offs

**Completeness threshold is simple.** The current completeness check is a set of field-presence rules with a minimum description length. It catches obvious gaps but not subtle ones such as a mitigation plan that merely restates the problem, or an impact score that is implausibly low for the described scenario. A more sophisticated check would use the LLM itself to critique the submission, at the cost of a longer pipeline and an additional LLM call on every create.

**Fallback perspectives are placeholders.** When no LLM is configured the fallback returns generic placeholder perspectives that meet the schema but carry no analytical value. They exist so the schema and the UI render correctly in the demo. A reviewer encountering fallback perspectives should request a fresh package once a provider is configured, rather than treating the placeholders as analysis.

**pgvector similarity is embedding-quality dependent.** The deterministic local embedding used in the demo maps text to a fixed vector using a hashing function. This is reproducible and zero-cost but has no semantic relationship to the risk text. In a production deployment this should be replaced with an embedding from the same provider used for analysis. The `cited_decision_ids` field in the package records which past decisions were retrieved, so the quality of retrieval can be audited.

**Past-decision hit rate is 0% in fallback evaluation.** The offline evaluator does not connect to a database. The golden set includes two cases where a similar past decision would be expected, but the fallback pipeline returns an empty list for `past_decisions` because there is nothing to query. A live evaluation against a seeded database would produce non-zero hit rates. The threshold for this metric is set at >= 0% for CI so the fallback evaluation passes; a production evaluation would set a higher threshold.

**Separation of duties is enforced in application code.** The two-reviewer requirement and the self-exclusion rule are checked in the API handler. They are not enforced at the database layer. A direct SQL write would bypass them. In a production deployment the decision table should have a trigger or a constraint that makes this invariant hard to circumvent.

## Evaluation

The risk package evaluator is in `backend/evaluations/eval_decision_packages.py`. It runs offline against a 25-case golden set (`backend/evaluations/risk_golden_set.json`) covering:

- Complete and incomplete submissions (3 cases with expected `needs_info=true`)
- Clear high-risk and low-risk cases
- Borderline cases where the score falls near treatment boundaries
- 3 prompt injection attempts embedded in different fields (description, proposed_mitigation, business_unit)
- 2 cases where a similar past decision would be expected

Metrics measured: completeness precision, completeness recall, schema validity, injection detection rate, no-auto-decision invariant, and past-decision hit rate in the top 3 results. Results are in `backend/evaluations/risk_results.json`. The script accepts `--provider openai|anthropic` to run against a live LLM; those results are written to a separate file and are never mixed with fallback numbers.

CI runs the script as part of the `backend-quality` job and fails the build if any metric falls below its threshold.
